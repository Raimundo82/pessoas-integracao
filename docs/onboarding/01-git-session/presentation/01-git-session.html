Install Git — Git vs Gitea vs GitHub

CONCEPT

Git is the tool you install. Gitea/GitHub are websites that host repositories.

Git

Command-line tool installed on your machine. Tracks changes, creates commits, manages branches. Works offline.

Gitea

Self-hosted web platform. Our internal server at devops-01.marinha.pt. Stores repos, runs CI/CD, manages PRs.

GitHub

Cloud-hosted version of the same idea (by Microsoft). Same Git concepts — just a different website.

You install Git once on your machine. Gitea and GitHub are the collaboration layer on top — PR reviews, pipelines, issues.

SSH Keys — Authenticate Without Passwords

CONCEPT

❌ HTTPS

Username + password (or token) on every push. Annoying and harder to manage securely.

✅ SSH

Cryptographic key pair — set up once, works forever. Zero friction on every push.

Key pair

Private key ~/.ssh/id_ed25519 — stays on your machine. Never share it.

Public key ~/.ssh/id_ed25519.pub — you give this to Gitea. Safe to share.

How SSH authentication works:

Your machine Gitea server "I want to push" ──────────────▶ ◀────────────── "Prove who you are" [signs w/ priv key] ──────────────▶ ◀────────────── "Verified ✅ Access granted" → No password needed. Ever.

SSH Keys

YOUR TURN
💻 YOUR TURN — Generate your key and register it on Gitea
1
ls ~/.ssh/
See id_ed25519 + id_ed25519.pub? Already have keys — skip to step 3.

cat ~/.ssh/id_ed25519.pub
Copy the output (starts with ssh-ed25519 AAAA...)

Paste your public key. Name it "My Laptop". Click Add Key.
5
ssh -T git@devops-01.marinha.pt
Expected: "Hi <username>! You've successfully authenticated." ✅

What cloning does

After cloning — one remote

origin — the shared repo

Push your branches here. Open PRs from here.

Our workflow

origin/master (shared repo) │ ▼ clone local master ← keep in sync │ └── feat/your-branch ← your work │ ▼ push + open PR → reviewed → merged to master
Everyone clones the same repo and works in branches. No forks needed.
Always git pull origin master before creating a new branch.

Key habits

  • Keep branches short-lived
  • One thing per branch
  • Delete the branch after merge

Gitflow

develop + release branches, complex merge ceremonies. We don't use this.

GitHub Flow ✅

Only master. Simple squash merge. master always reflects what's running.

Conventional Branching — Naming Branches

CONCEPT
<type>/<kebab-case-description> e.g. feat/add-employee-address-field
feat / featureNew functionality
fix / bugfix / hotfixBug fixes
refactorCode restructure, no behaviour change
testAdding or fixing tests
docsDocumentation only
ciPipeline / workflow changes
choreDependencies, tooling, config
⚠️ branch-name-lint validates every branch name when a PR is opened. Invalid name = pipeline fails before anything else runs.

Semantic Commits — Conventional Commits Standard

CONCEPT
<type>: <short description> lowercase · under 72 chars · no period at end

Real examples from this project

feat:feat: add GetEmployeeByNi GraphQL query
fix:fix: throw EmployeeByNiNotFoundException
test:test: add snapshot for FetchAllEmployeesSorted
refactor:refactor: extract dbContext to DisposeAsync
ci:ci: add Trivy scan to PR workflow

Impact on semantic versioning

feat:Minor bump — 1.0.0 → 1.1.0
fix: / perf:Patch bump — 1.0.0 → 1.0.1
BREAKING CHANGEMajor bump — 1.0.0 → 2.0.0
othersNo version bump
pull-request-lint validates the PR title against this standard — the title becomes the squash-merge commit on master.

Create a Pull Request — The Merge Proposal

CONCEPT

A PR is a formal proposal to merge your branch into master — where checks run and code review happens.

PR lifecycle

1
Push branch to your fork
2
Open PR on Gitea
3
Pipeline runs automatically
4
Reviewer comments
5
Fix & re-push
6
All green + approved → Squash merge
7
Delete branch

What makes a good PR

Title✅ feat: add GetEmployeeByNumsap query
❌ "my changes"
Size✅ One logical change
❌ Months of work in one PR
Checklist✅ Filled in
❌ Ignored
Branch✅ feat/add-numsap-query
❌ master or dev
Direct pushes to master are BLOCKED. All changes go through PRs.
